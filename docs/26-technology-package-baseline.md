# Technology and Package Baseline

## Purpose

K-Nex needs a conservative implementation baseline built from mature, widely adopted, well-maintained packages that reinforce the architecture already accepted in this repository.

The baseline must not turn K-Nex into:

```text
an ORM abstraction above Payload
an editor-engine-specific platform
a component-library-specific design system
a Redux application with global business state
a client-side analytics/query engine
a realtime system whose socket transport is the source of truth
a collection of newly released major versions adopted without qualification
```

The selected packages are implementation details behind K-Nex contracts. Plugins and stored documents continue to depend on K-Nex IDs, schemas, capabilities, output contracts, semantic primitives, and service interfaces rather than third-party library types.

## Status

This document records the accepted default package families for the first implementation and POC.

Exact patch versions are not hard-coded here. The implementation repository and generated customer applications must pin a tested compatibility set in `package.json`, `pnpm-lock.yaml`, generated build inventory, and CI fixtures.

The baseline is dated **2026-08-25**. New major versions require the adoption process defined later in this document.

# Selection principles

## 1. K-Nex contracts own the architecture

Third-party APIs must not become persisted or cross-package K-Nex contracts.

Examples:

```text
Allowed:
  DataTable consumes table.records@1
  realtime provider implements RealtimeGateway
  source client consumes DataSourceEnvelope
  theme implements semantic Button/Card/DataTable primitives

Forbidden:
  plugin block props contain EChartsOption
  plugin public API returns QueryObserverResult
  layout stores Socket.IO event names generated by users
  module contract exports TanStack ColumnDef
  domain plugin imports Puck ComponentConfig
  K-Nex output contract exposes Zustand StoreApi
```

Each selected library must be isolated behind a K-Nex-owned adapter, service, package boundary, or generated integration layer.

## 2. Prefer one proven owner per concern

Do not install overlapping libraries without a documented role.

```text
Zod            owns first-party schema authoring/runtime parsing
Ajv            owns compiled validation of generated static JSON Schema
TanStack Query owns remote/server state
Zustand        owns ephemeral local coordination state
React Hook Form owns form interaction state
Payload Jobs   owns durable/retryable application jobs in V1
Pino           owns structured logs
OpenTelemetry  owns trace/metric interoperability
```

## 3. Framework-native behavior wins over duplicate abstraction

Payload already owns database adapters, Local API/request context, collection access, transactions, migrations, admin integration, and jobs. K-Nex composes these capabilities rather than wrapping them with parallel frameworks.

## 4. Stable major does not automatically mean immediate adoption

A newly stable major can be technically excellent while still lacking ecosystem soak time. Major upgrades require fixture, compatibility, bundle, migration, and customer-upgrade evidence.

## 5. Server remains authoritative

Client libraries improve rendering, caching, and interaction. They never become the authorization, business transaction, or data-consistency boundary.

# Runtime and framework

## Node.js 24 LTS

Use Node.js 24 LTS for the first implementation and generated production applications.

Reasons:

- it is an active LTS line as of the baseline date;
- Node.js production guidance recommends active or maintenance LTS releases;
- Node.js 20 is already end-of-life and must not be selected for new generated projects;
- it aligns with modern ESM, `fetch`, Web Crypto/`crypto`, `AsyncLocalStorage`, test tooling, and current package requirements.

Repository requirements:

```text
.nvmrc or .node-version
package.json engines.node
Dockerfile base image
CI matrix
build manifest
```

must agree on the supported Node line.

Do not use the Node 26 Current line for production until it becomes LTS and passes the K-Nex compatibility matrix.

## Payload, Next.js, and React

Payload remains the framework foundation. The scaffold must select an exact tested tuple:

```text
Payload version
Next.js version supported by that Payload release
React/React DOM versions supported by that tuple
@payloadcms/db-postgres version
Node.js version
```

Rules:

- never generate `latest` ranges;
- do not independently upgrade Next.js beyond Payload's supported range;
- core/plugins declare compatible Payload ranges but customer applications pin exact versions;
- framework upgrades run both clean-install and previous-customer-version migration fixtures;
- Payload admin/server-component boundaries remain authoritative over arbitrary client-library convenience.

## Payload Postgres adapter

Install `@payloadcms/db-postgres` directly during scaffold generation. Modules query through `req.payload`, Payload Local API, and module domain/query services.

No Prisma, Drizzle, TypeORM, Knex, or K-Nex repository abstraction is introduced for the primary application model.

A module may use carefully reviewed adapter-specific behavior internally when necessary, but its public K-Nex contract remains defined by module semantics rather than SQL or ORM APIs.

## Payload rich text and image processing

Recommended optional framework packages:

```text
@payloadcms/richtext-lexical
  default rich-text implementation when CMS rich text is enabled

sharp
  installed only when generated application features require image processing
```

Do not install optional native/image dependencies in every backend-only project.

# Monorepo, package, and release tooling

## pnpm workspaces

Use pnpm workspaces as the package manager and monorepo foundation.

Rules:

- pin the exact pnpm version through `packageManager` and Corepack-compatible metadata;
- commit `pnpm-lock.yaml`;
- use `workspace:` protocol for internal first-party dependencies;
- enable strict peer dependency handling in CI;
- disallow workspace dependency cycles;
- use a reviewed install-script allowlist for packages that genuinely require builds;
- use `minimumReleaseAge` for ordinary dependency updates, with an explicit emergency security override;
- generated customer applications pin exact direct dependency versions.

## Turborepo

Use Turborepo for task dependency graphs and local/CI caching:

```text
build
typecheck
lint
test
contract-test
package-check
generate
```

Turborepo does not own package boundaries, versioning, or runtime configuration. It orchestrates scripts already defined by each workspace.

## Changesets

Use `@changesets/cli` for first-party package version planning and changelogs.

Required policy:

- package versions can advance independently;
- every externally visible contract change includes a changeset;
- breaking K-Nex contract changes require major versions and migration notes;
- internal refactors without package API effect can omit release changes;
- customer applications consume exact released package versions rather than floating workspace state.

## Package output

Prefer ESM-first package output generated by TypeScript project builds. Do not introduce a new bundler for every package by default.

Use:

```text
tsc project references / declaration emission
explicit package exports
server/client/ui subpath exports
publint
@arethetypeswrong/cli
```

Bundle only packages that prove a measurable need, such as a standalone CLI distribution. A bundler selection is package-specific and does not become a platform runtime contract.

# Schema and validation stack

## Zod 4 as the authoring source of truth

Use Zod 4 for first-party TypeScript schema authoring:

```text
plugin options
customer extension options
data-source inputs
source-specific outputs
canonical output contracts
actions
UI state definitions
theme token profiles
environment parsing
runtime settings
```

Why it fits K-Nex:

- TypeScript-first static inference;
- runtime parsing at trust boundaries;
- browser and Node support;
- zero external dependencies;
- stable Zod 4 line;
- built-in JSON Schema conversion support;
- broad ecosystem support, including React Hook Form resolvers.

Rules:

- first-party schemas are authored once in Zod;
- no parallel hand-maintained Zod and JSON Schema definitions for the same contract;
- source output uses `parse`/`safeParse` at the trusted gateway boundary;
- transformations/coercion are explicit and must not silently alter persisted contract meaning;
- reusable K-Nex schema helpers restrict unsafe or non-portable patterns where JSON Schema export is required.

## Ajv 8 for static JSON artifacts

Use Ajv 8 with `ajv-formats` to validate generated/static JSON artifacts:

```text
k-nex.app.json
k-nex.plugin.json
catalog entries
build manifests
exported JSON Schemas
generated descriptor artifacts
non-TypeScript tooling inputs
```

Ajv exists for this specific role because it is a mature, standards-oriented JSON Schema validator that compiles schemas to optimized validation functions.

Rules:

- compile once and reuse; never compile a schema on every HTTP request;
- use strict mode;
- disable implicit coercion, removal, and default mutation unless a specific migration tool requests them;
- allow only reviewed formats;
- generated standalone validators may be used by CLI artifacts when this improves startup/performance;
- Ajv does not become a second schema-authoring language.

## Schema flow

```text
Zod source schema
        ↓
TypeScript inferred types
        ↓
Zod runtime parser for TypeScript/server/browser boundaries
        ↓
Generated JSON Schema for static manifests/tool interoperability
        ↓
Ajv compiled validator for JSON artifacts
```

# Server state, local UI state, and forms

## TanStack Query 5 for server state

Use `@tanstack/react-query` v5 for data-source results, cache lifecycle, request deduplication, retry policy, background refetch, hydration, and invalidation.

This directly matches the accepted K-Nex realtime model:

```text
mutation commits
  → authorized invalidation message
  → K-Nex query-key matcher marks source query stale
  → TanStack Query refetches the authenticated source gateway
  → canonical output validation runs
  → component rerenders
```

Architectural boundary:

- K-Nex owns `createDataSourceQueryKey`, source clients, error mapping, actor-scope rules, and invalidation matching;
- plugins and stored documents never reference TanStack Query keys or types;
- internal authenticated results default to actor-scoped or no-store policies;
- SSR dehydration must never share one user's protected result with another user;
- retries do not apply blindly to authorization, validation, or non-idempotent operations;
- native `fetch` is the HTTP implementation; Axios is not required.

## Zustand 5 for ephemeral UI coordination

Use Zustand vanilla stores, created per page/workspace/document provider, for:

```text
date filters
selected stage/branch
expanded builder node
local panel state
allowed user personalization state
component-to-component selections
```

Do not use Zustand for:

```text
Payload documents
server/data-source results
permissions
business transactions
realtime authority
cross-request global state
```

Next.js rules:

- no module-global mutable store shared between requests;
- create stores per document/request/provider;
- React Server Components do not read/write Zustand;
- hydration uses identical validated initial state;
- persistence is explicit by K-Nex state policy (`url`, `session`, `user-preference`, or none), not automatic global middleware use.

K-Nex state contracts must not expose `StoreApi` or Zustand middleware types.

## React Hook Form

Use React Hook Form for client-side form interaction and `@hookform/resolvers/zod` for Zod integration.

Suitable uses:

```text
plugin settings
builder property editors
theme token forms
filter forms
module operational forms where Payload/custom screens need local form control
```

Rules:

- server handlers revalidate with Zod;
- client validation is UX, not security;
- avoid duplicating React Hook Form state inside Zustand;
- use React Aria form primitives/semantics for accessibility;
- do not adopt TanStack Form v2 while it remains a newly released/pre-stable line.

# Accessible UI and design-system foundation

## React Aria Components

Use `react-aria-components` as the default accessible behavior/semantic foundation for K-Nex primitives.

It fits the accepted theme architecture because it provides accessible composable behavior while allowing custom styling.

Use it for appropriate primitives such as:

```text
Button
Link
Dialog/Modal
Popover/Tooltip
Menu
ListBox/ComboBox/Select
Tabs
Checkbox/Radio/Switch
Date and time inputs
Disclosure
DropZone/FileTrigger
focus and keyboard behavior
```

Do **not** use Adobe React Spectrum/Spectrum 2 as the K-Nex design system. React Spectrum carries an Adobe visual language; K-Nex needs Minimal, Neobrutalism, Glassmorphism, and customer-specific themes.

Rules:

- K-Nex semantic primitives wrap React Aria Components;
- theme packages own CSS variables, recipes, and visual variants;
- customer modules import K-Nex primitives, not React Aria directly where a semantic K-Nex primitive exists;
- alpha/beta React Aria components are excluded from the stable primitive set until promoted and tested;
- advanced DataTable state is not split blindly between React Aria Table and TanStack Table; K-Nex owns one composed table adapter and its accessibility tests.

## Styling baseline

Use:

```text
CSS custom properties for runtime theme tokens
CSS Modules or local plain CSS for structural styles
semantic data attributes/slots for variants
```

Tailwind can be selected inside a customer repository or a specific theme implementation, but Tailwind classes do not become K-Nex module contracts, persisted theme data, or required core output.

Avoid a core dependency on MUI, Chakra UI, Ant Design, or another visually opinionated component system because that would fight the theme-plugin model.

# Data tables

## TanStack Table 8 initially

Use `@tanstack/react-table` v8 for the first POC and V1 DataTable adapter.

Rationale:

- mature and widely deployed;
- headless, so it does not impose a design system;
- supports controlled/manual sorting, filtering, pagination, visibility, resizing, and selection;
- maps cleanly to `table.records@1` and source-declared field metadata.

TanStack Table v9 became stable on 2026-08-04 and includes substantial architecture/performance improvements. It is promising but too recent to become the initial frozen customer baseline without a soak/compatibility gate.

Adoption policy:

```text
initial implementation: v8 behind @k-nex/ui-data-table
parallel benchmark/compatibility fixture: v9
adopt v9 only after ecosystem soak and all K-Nex table fixtures pass
no plugin public API exposes v8 or v9 ColumnDef/Table types
```

Data-source-backed tables use manual/server mode by default. Client-side aggregation/sorting over large or sensitive source records is not the platform default.

## TanStack Virtual

Use `@tanstack/react-virtual` for measured large-table/list rendering needs.

Virtualization is an implementation detail of the K-Nex table/list primitive. It must not change source pagination contracts or accessibility semantics.

# Visualization

## Apache ECharts 6

Use Apache ECharts behind `@k-nex/ui-visualization-echarts` or an equivalent internal adapter.

Why it fits:

- mature Apache project;
- broad chart coverage;
- Canvas and SVG renderers;
- progressive/large-data capabilities;
- responsive configuration;
- accessibility features;
- sufficient flexibility for customer theme adaptation.

Strict boundary:

```text
stored document
  contains K-Nex block props + source binding
        ↓
canonical metric/series contract
        ↓
K-Nex visualization adapter
        ↓
trusted generated ECharts option
```

Never store or accept arbitrary user-authored ECharts options, formatter functions, HTML, JavaScript callbacks, external URLs, or executable transforms in builder documents.

Rules:

- use tree-shakable ECharts core imports;
- enable ECharts ARIA support in the K-Nex adapter;
- provide semantic/tabular fallback or summary for charts;
- use decal/pattern support where color alone is insufficient;
- prefer Canvas for large element counts and evaluate SVG for smaller/SSR/export cases;
- map ECharts events into versioned K-Nex block output ports;
- no third-party React wrapper is required; K-Nex owns a thin lifecycle/resize adapter.

# Realtime

## Socket.IO 4 as the first provider implementation

Use Socket.IO 4 for the first implementation of `realtime.gateway`.

The first provider should be identified as Socket.IO-based rather than described as a raw WebSocket protocol implementation:

```text
plugin ID: provider.realtime.socketio
package:   @k-nex/provider-realtime-socketio
capability: realtime.gateway@1
```

Why it fits the first customer/deployment model:

- WebSocket transport in normal operation;
- reconnect behavior and fallback transport;
- rooms/namespaces/middleware useful for authorized scopes;
- mature client/server ecosystem;
- official multi-server adapters;
- enough operational ergonomics for independently deployed customer applications.

Architectural rules:

- modules depend on `RealtimeGateway`, not Socket.IO classes;
- modules publish typed K-Nex invalidation/stream messages;
- the provider authenticates through Payload session/token policy;
- every subscription is authorized by source/topic/record scope;
- full business records are not pushed for ordinary tables/counters/charts;
- reconnect always triggers authoritative source resynchronization;
- connection-state recovery is an optimization, never the consistency guarantee;
- Socket.IO types cannot appear in plugin contracts or stored documents.

## Single-instance mode

Use Socket.IO's in-memory adapter for small single-instance deployments.

## Multi-instance mode

Use:

```text
@socket.io/redis-adapter
ioredis
Redis 7 sharded Pub/Sub adapter where supported
```

The Redis adapter carries messages between instances; it does not become the business event store or source of truth.

Because distributed Pub/Sub can miss messages during disconnect/recovery paths, the K-Nex client must invalidate/refetch or resnapshot after reconnect.

## Raw WebSocket future provider

A `ws`-based provider may be evaluated later for high-frequency tracking or constrained clients only after benchmarks show Socket.IO overhead is material. It must implement the same `realtime.gateway` contract.

# Jobs and workflows

## Payload Jobs Queue first

Use Payload's built-in Jobs Queue for the first implementation:

```text
scheduled jobs
retryable module work
imports/exports
notifications
outbox processing
projection rebuilds
cleanup/retention
integration synchronization
```

Generated deployment profiles should support separate commands/processes for:

```text
web
worker
scheduler/cron trigger
```

Do not add BullMQ, Temporal, or another workflow framework until a measured requirement exceeds Payload Jobs capabilities, such as cross-service durable orchestration, extreme throughput, or a customer deployment constraint.

External job infrastructure, if later required, should be a provider behind K-Nex job/workflow contracts rather than a rewrite of module business services.

# Logging and observability

## Pino

Use Pino for structured server/CLI logs.

Rules:

- JSON logs in production;
- `pino-pretty` only for local development;
- child loggers include application ID, plugin ID, source/action ID, correlation ID, actor type, and job ID where applicable;
- redact secrets, authorization headers, cookies, database URLs, and configured sensitive fields;
- log processing/export runs outside the hot request path where possible;
- no plugin creates an unrelated logger stack.

## OpenTelemetry

Core packages may depend on `@opentelemetry/api` for neutral tracing/metrics hooks. The customer/deployment application selects SDK, exporter, sampling, and collector configuration.

V1 policy:

- server traces and metrics are supported;
- Pino remains the log implementation because OpenTelemetry JavaScript logs are not yet at the same stable maturity as traces/metrics;
- browser auto-instrumentation is not enabled by default;
- no vendor-specific exporter is required by core;
- absence of an OpenTelemetry SDK must not break application behavior.

Use native `AsyncLocalStorage` for request/correlation context where appropriate.

# Dependency and upgrade policy

## Exact versions in customer applications

Generated customer repositories use exact direct versions and commit the lockfile.

First-party packages can declare peer ranges where ecosystem coexistence requires it, but the generated application resolves one exact tested tuple.

## Upgrade classes

```text
Patch
  automated PR allowed after minimum release age and tests

Minor
  automated/grouped PR allowed after changelog review and full CI

Major
  manual architecture/compatibility review, migration fixture, and ADR/decision update when material

Security emergency
  minimum release age can be bypassed with explicit review and documented reason
```

## New-major soak gate

A newly stable major is adopted only after:

```text
official stable declaration
minimum ecosystem soak period appropriate to risk
Payload/Next/React compatibility
clean and upgrade fixtures
bundle/runtime benchmark
SSR/RSC compatibility
accessibility tests
stored document/migration compatibility
customer-app smoke test
rollback plan
```

This policy currently keeps TanStack Table v8 as the initial implementation even though v9 is stable and promising.

## Automated dependency management

Renovate is the preferred automation service because grouped package rules can keep framework tuples and K-Nex package families aligned. Dependabot is an acceptable fallback when organizational policy prefers only GitHub-native configuration.

Automation never auto-merges framework, Payload, builder, table, schema, realtime, or migration-sensitive major versions.

# POC acceptance gates

The baseline is accepted only if the implementation proves:

## Framework and validation

- Node 24/Payload/Next/React exact tuple builds and runs;
- Zod schemas generate usable JSON Schema for selected artifacts;
- Ajv strict compiled validators reject malformed manifests without mutation;
- source results fail closed when either exact schema or output contract fails.

## UI and state

- React Aria-based primitives render correctly under Minimal and Neobrutalism themes;
- TanStack Query caches/deduplicates actor-scoped source results and handles invalidation;
- Zustand page state is per document/provider and creates no cross-request hydration leak;
- React Hook Form property editors preserve Zod/server validation;
- TanStack Table v8 handles server pagination, selected stable fields, sorting, filtering, resizing, and permission changes;
- large table fixture can enable virtualization without breaking keyboard/screen-reader behavior.

## Visualization

- canonical category/time series render through ECharts without raw option storage;
- ARIA description and fallback summary are present;
- theme tokens map deterministically;
- malicious labels/metadata cannot become executable formatter/HTML behavior.

## Realtime

- Socket.IO provider authenticates Payload actors;
- unauthorized subscriptions fail;
- single-instance invalidation works;
- Redis-backed multi-instance invalidation works;
- disconnect/reconnect refetches authoritative source results;
- module code contains no Socket.IO imports.

## Testing and package integrity

- Vitest contract suites run across core and plugins;
- Playwright covers auth/builder/source/realtime journeys;
- Testcontainers proves real Postgres migrations/transactions;
- dependency-cruiser fails deliberate forbidden imports;
- publint and Are the Types Wrong pass packed first-party packages;
- a generated customer fixture installs only exact tested versions.

# Revisit triggers

Revisit a baseline package when:

```text
security support ends
maintainer/project health materially declines
Payload/Next compatibility breaks
measured performance is insufficient
accessibility requirements cannot be met
required deployment topology is unsupported
package types leak despite adapter boundary
migration/upgrade burden exceeds replacement cost
a stable major completes the adoption gate
```

A replacement must preserve K-Nex contracts and stored-document compatibility wherever possible.
